# MiniDSP — 3-hour AI Developer Challenge (simplified)

**Objective:** Build a working, tested, documented MiniDSP web app using two GitHub Copilot chats and human judgement. This is a competition, not a compliance paperwork exercise.

## The entire workflow
1. Open the project in VS Code. Open GitHub Copilot Chat 1 in Ask mode (Instructor). Paste `START_HERE_INSTRUCTOR.md`.
2. Instructor proposes a small next task and gives a copy-ready prompt.
3. Paste that prompt into a separate GitHub Copilot Chat 2 in Agent mode (Developer). Agent implements, tests and records progress.
4. Paste Agent's response into Instructor. Instructor challenges assumptions, code, tests, security and gaps; gives a focused follow-up if needed.
5. Repeat until working; the human developer orchestrates, reviews and decides what to approve and when to commit/deploy.

**Don't paste raw uploaded file content, credentials or personal data into either AI chat.** Only synthetic training files may be used.

## Files
- `START_HERE_INSTRUCTOR.md` — paste once into Chat 1
- `START_HERE_DEVELOPER.md` — paste once into Chat 2, before its first task
- `PRODUCT_BRIEF.md` — functionality, safety and acceptance criteria
- `CHALLENGE_TIMELINE.md` — timeboxes and priority
- `DESIGN_REFERENCE.md` — facilitator fills in actual design-system paths and live URL
- `WORK_LOG.md` — Agent maintains short, honest progress/test/decision log
- `LEARNINGS.md` — Agent helps developer capture lessons
- `DEVELOPER_SCORECARD.md` — generated by the Agent at the end of the challenge only
- `FOR_SUNJEEV.md` — setup checklist and facilitator instructions
- `DEVELOPER_QUICK_GUIDE.md` — one-page instructions
- `tests/fixtures/` — starter synthetic files; optional withheld acceptance pack provided separately

The facilitator must supply a working starter project and real Lepide design references. This package is **documentation only**, not a preconfigured Next.js application. Do not assume any service is connected.

## MiniDSP app

### Setup
1. Node 24+ and npm. `npm install`.
2. Copy `.env.example` → `.env.local` and set `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` (anon/publishable key only — never a service_role key).
3. In the Supabase SQL Editor run [`supabase/migrations/0001_init.sql`](supabase/migrations/0001_init.sql). Create users either at `/signup` or in Supabase (Authentication → Users, auto-confirm). For the RLS and E2E tests add `TEST_USER_A_EMAIL/PASSWORD` and `TEST_USER_B_EMAIL/PASSWORD` to `.env.local`.
4. Sign-up email confirmation: with **Confirm email** on (Supabase → Authentication → Sign In / Providers → Email), `/signup` shows "Check your email" and the link lands on `/auth/confirm`. Add `http://localhost:8050/**` (and your Vercel URL) to Authentication → URL Configuration → Redirect URLs. With it off, new users are signed straight in.
5. `npm run dev` → http://localhost:8050.
6. Behind a TLS-inspecting corporate proxy, set `NODE_USE_SYSTEM_CA=1` so Node trusts the OS certificate store.

### Architecture
- **Next.js 16 App Router** (`src/app`). Pages: `/login`, `/signup`, `/dashboard`, `/upload`, `/findings`. Routes: `POST /api/scan`, `GET /api/export`, `GET /auth/confirm`.
- **Auth:** Supabase email/password via `@supabase/ssr` (sign-up with server-side validation: valid email, 8–72-byte password, confirmation match). `src/proxy.ts` refreshes the session cookie; every page/API checks `supabase.auth.getUser()` on the server (redirect or 401).
- **Scanning:** `src/lib/upload/validate.ts` (type, 1 B–1 MiB, binary/UTF-8 checks) → `src/lib/detectors` (`scanText`: card → NINO → phone → email, non-overlapping, Luhn) → masked, aggregated findings → `save_scan` RPC (one transaction). The uploaded file is never stored. `/upload` also offers **Scan a folder**: the browser's folder picker selects every `.csv`/`.txt` (max 50), and each file is sent separately to `POST /api/scan`, so the same server validation applies; other files are listed as skipped.
- **Data:** `public.scans` and `public.findings` with owner-scoped RLS and a composite FK so a finding can only attach to its owner's scan.
- **UI:** Lepidus design system (`lepidus.css` / `lepidus.js` from https://lepide-design-system.vercel.app/v1/), documented `lp-*` classes and tokens only — see `DESIGN_REFERENCE.md`.
- **Export:** RFC 4180 CSV, every field quoted, spreadsheet formulas neutralised.

### Security
- Only masked values (`j***@example.com`, `07******321`, `AB******C`, `************1111`) and counts are returned, stored, logged or exported. Raw matches never leave `scanText`.
- All validation and scanning happen on the server; client checks are hints only. Invalid uploads make no database call.
- RLS on every table; the app uses only the anon key + the user's session. `save_scan` is `security invoker`.
- Secrets live in `.env` / `.env.local` (git-ignored). Synthetic data only.

### Known limitations
- Detectors are format-based (no NINO allocation checks, no card BIN checks); see `WORK_LOG.md` for edge cases.
- `/findings` shows the 200 most recent matches (no pagination); export is capped at 50,000 rows.
- Light theme only; charts are shown as tables (Lepidus charts are React-only).
- Chunked uploads without `Content-Length` are buffered by the Next proxy (up to 10 MB) before the route's 1 MiB cap applies.
- See `WORK_LOG.md` for what is verified, skipped or unverified.
